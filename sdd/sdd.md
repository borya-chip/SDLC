## 1. Введение {#1-introduction}

### 1.1 Назначение документа {#11-document-purpose}

Документ описывает устройство CarKeeper 1.0, требования к которому заданы в `srs/srs.md` (версия 0.2.1). По нему исполнитель реализует систему, junior-разработчик получает границы своих задач, тестировщик выбирает уровни проверок, а Заказчик видит, на чём основаны оценки плана `plan/release-plan.md`. Документ составлен по IEEE 1016 и шаблону курса `sdd/sdd-template.md`.

### 1.2 Область применения {#12-subject-scope}

Проектируется веб-приложение CarKeeper версии 1.0 для частных владельцев одного–трёх автомобилей. Оно ведёт гараж и показания пробега, строит план ТО по регламенту, рассчитывает срок каждой работы по пробегу и времени, хранит журнал обслуживания с расходниками и вложениями, напоминает о сроках на панели и по e-mail, показывает календарь, сезонную смену шин и сроки документов, строит отчёт и прогноз расходов, выгружает историю в PDF и CSV.

Не входит: считывание пробега через OBD, онлайн-запись на СТО, покупка запчастей, распознавание чеков, мобильное приложение, общий доступ к автомобилю нескольких пользователей (раздел 1.2 SRS).

## 2. Обзор дизайна {#2-design-overview}

CarKeeper – одно приложение Spring Boot 3 на Java 21 со страницами Thymeleaf (ограничение C-1 SRS), разделённое на функциональные модули со слоями «контроллер – сервис – репозиторий». Расчёт сроков вынесен в независимый модуль `maintenance-core`. Данные хранятся в PostgreSQL 16, вложения – в каталоге на том же сервере, единственная внешняя система – SMTP-сервер.

### 2.1 Задачи стейкхолдеров {#21-stakeholder-concerns}

| Стейкхолдер | Основные задачи | Точки зрения |
|-------------|-----------------|--------------|
| Заказчик (владелец продукта) | Состав версии, сроки демонстраций, надёжность напоминаний, стоимость | Контекст, динамика состояний, развёртывание |
| Владелец автомобиля | Верные сроки, сохранность истории, работа со смартфона | Контекст, алгоритм, интерфейс |
| Исполнитель (архитектор, разработчик) | Границы модулей, данные, транзакции, параллельные запросы | Все выбранные |
| Junior-разработчик | Изолированные задачи с понятными входами и выходами | Композиция, интерфейс |
| Тестировщик | Формулы и контрольные примеры, сценарии отказов | Алгоритм, взаимодействие, динамика состояний |
| Сопровождающий | Развёртывание, резервные копии, журналы и метрики | Зависимости, информация, развёртывание |

## 3. Проектные представления {#3-design-views}

### 001-context

- **ID**: 001-context
- **Title**: Границы CarKeeper и окружение
- **Viewpoint**: Контекст (2.2.1)
- **Representation**:

| Актор / система | Взаимодействие | Требования |
|-----------------|----------------|------------|
| Владелец автомобиля | Браузер по HTTPS: гараж, пробег, план, журнал, отчёты | REQ-FUNC-001…020, REQ-SEC-002 |
| Администратор | Браузер: справочник регламентов, учётные записи | REQ-FUNC-002, 005 |
| SMTP-сервер | Приём писем через STARTTLS, порт 587, таймаут 10 с | REQ-INT-004, REQ-FUNC-011 |
| Файловое хранилище сервера | Вложения вне веб-каталога, резервные копии | REQ-INT-005, REQ-SEC-006, REQ-REL-003 |

- **More Information**: гость видит только главную страницу, регистрацию и вход (раздел 2.4 SRS). Других внешних систем нет, платные API не используются (C-7).

### 002-composition

- **Title**: Модули приложения
- **Viewpoint**: Композиция (2.2.2)
- **Representation**:

| Модуль | Ответственность | Требования SRS | Решения |
|--------|-----------------|----------------|---------|
| Веб-интерфейс | Страницы Thymeleaf, проверка полей, вывод статусов цветом и текстом | REQ-INT-001…003 | — |
| Доступ | Регистрация, вход, роли, проверка владельца, блокировка после 5 попыток | REQ-FUNC-001, 002, REQ-SEC-001…005 | — |
| Автомобили | Карточки автомобилей, показания пробега, средний пробег | REQ-FUNC-003, 004 | 002 |
| План ТО | Регламенты, план автомобиля, календарь, шины, документы | REQ-FUNC-005, 006, 016, 019, 020 | 001 |

### 003-dependency

- **ID**: 003-dependency
- **Title**: Направление зависимостей
- **Viewpoint**: Зависимости (2.2.6)
- **Representation**:

| Элемент | Зависит от | Правило |
|---------|------------|---------|
| Контроллеры | Сервисы | Контроллер не обращается к репозиториям напрямую (REQ-MAINT-002) |
| Сервисы | Репозитории, `maintenance-core` | Сервис загружает данные и вызывает расчёт |
| Уведомления, План ТО | `maintenance-core` | Один расчёт для панели, плана и писем |
| Отчётность | Журнал, Автомобили (только чтение) | Отчёты не изменяют данные |
| `maintenance-core` | только JDK | Нет Spring, JDBC, сети (ADR-0001) |

- **More Information**: правило проверяется сборкой: `maintenance-core` – отдельный модуль Maven без зависимостей на Spring.

### 004-information

- **ID**: 004-information
- **Title**: Модель данных PostgreSQL
- **Viewpoint**: Информация (2.2.7)
- **Representation**:

| Сущность | Ключевые поля | Правила |
|----------|---------------|---------|
| User | e-mail (уникальный), хеш bcrypt, роль, пороги статусов | REQ-SEC-001, REQ-FUNC-008 |
| Car | владелец, марка, модель, тип двигателя, VIN, годовой пробег, архив | Удаление – перевод в архив |
| MileageReading | автомобиль, дата, пробег | Не меньше предыдущего, не больше +5000 км в сутки |
| Regulation, RegulationItem | тип двигателя, работа, интервалы км и месяцы | Хотя бы один интервал |
| PlanItem | автомобиль, работа, интервалы, последнее выполнение, отключена | Копия RegulationItem при добавлении автомобиля |
| ServiceRecord, RecordPart | дата, пробег, место, работы, расходники с артикулами, стоимость | Итог считается автоматически |
| Attachment | запись, случайное имя файла, тип по содержимому | До 5 файлов по 10 МБ, вне веб-каталога |
| Notification | позиция, цикл, статус, прочитано | Уникален (позиция, цикл, статус) – ADR-0003 |
| MailJob | пользователь, состав письма, попытки, следующая попытка | Повторы 1, 5, 25 мин |
| TyreSet, CarDocument | комплект шин и его пробег; документ и дата окончания | REQ-FUNC-019, 020 |

- **More Information**: схема версионируется миграциями Flyway (ограничение C-2); в журналы не попадают e-mail, VIN и госномер (REQ-OBS-001).

- **ID**: 005-interface
- **Title**: Внешние интерфейсы
- **Viewpoint**: Интерфейс (2.2.8)
- **Representation**:

| ID | Направление | Описание | Модуль | Требования |
|----|-------------|----------|--------|------------|

| IF-5 | Приложение ↔ пользователь | CSV журнала: UTF-8, разделитель «;», отчёт об ошибочных строках | Отчётность | REQ-FUNC-017 |

- **More Information**: все страницы русскоязычные, даты ДД.ММ.ГГГГ, суммы в BYN (REQ-COMP-002).

### 006-interaction

- **ID**: 006-interaction
- **Title**: Ключевые сценарии
- **Viewpoint**: Взаимодействие (2.2.9)
- **Representation**:

*Сценарий 1. Сохранение обслуживания (REQ-FUNC-009, 010, ADR-0002).*

1. Контроллер проверяет поля формы и передаёт команду сервису журнала.
2. Сервис открывает транзакцию, проверяет владельца и блокирует строку автомобиля.
3. Сохраняются запись и расходники, добавляется показание пробега, у отмеченных позиций обновляется последнее выполнение.
4. `maintenance-core` пересчитывает сроки и статусы этих позиций; транзакция фиксируется. Ошибка на любом шаге откатывает всё.

*Сценарий 2. Ежедневная проверка и напоминание (REQ-FUNC-011, 012, ADR-0003).*

1. В 08:00 по времени пользователя планировщик пакетами пересчитывает статусы позиций.
2. Для каждого перехода в «Скоро» или «Просрочено» создаётся событие с уникальным ключом; повтор после перезапуска ключ отбрасывает.
3. Событие сразу видно на панели; для владельца создаётся одно задание на письмо со списком переходов.
4. Планировщик отправки передаёт письмо на SMTP; при ошибке повторяет через 1, 5 и 25 мин, затем помечает задание ошибкой и пишет в журнал.

- **More Information**: напоминания о шинах и документах (REQ-FUNC-019, 020) создают события того же типа и проходят шаги 2–4.

### 007-algorithm

- **ID**: 007-algorithm
- **Title**: Расчёт срока и статуса позиции
- **Viewpoint**: Алгоритм (2.2.10)
- **Representation**:

1. Средний суточный пробег v = (M₂ − M₁) / (D₂ − D₁) по самому раннему и последнему показаниям за 90 дней; если показаний меньше двух или они охватывают меньше 7 дней – годовой пробег / 365 (REQ-FUNC-004).
2. M_next = M_last + L, D_next = D_last + T; для невыполнявшейся позиции M_last и D_last – пробег и дата добавления автомобиля.
3. D_M = D_cur + ⌈(M_next − M_cur) / v⌉; срок позиции – более ранняя из D_next и D_M; при отсутствии одного из интервалов используется другой (REQ-FUNC-007).
4. Статус: «Просрочено», если M_cur ≥ M_next или сегодня ≥ D_next; иначе «Скоро», если осталось ≤ 1000 км или ≤ 30 дней (пороги пользователя 100–5000 км, 7–90 дней); иначе «В норме» (REQ-FUNC-008).

- **More Information**: правильность проверяется шестью контрольными примерами таблицы Б.2 SRS; входные данные передаются явно, текущая дата – параметром, поэтому тесты детерминированы.

### 008-state-dynamics

- **ID**: 008-state-dynamics
- **Title**: Состояния позиции плана и задания на письмо
- **Viewpoint**: Динамика состояний (2.2.11)
- **Representation**:

| Объект | Переход | Условие | Следствие |
|--------|---------|---------|-----------|
| Позиция плана | «В норме» → «Скоро» | Достигнут порог по км или дням | Событие и задание на письмо |

## 4. Решения {#4-decisions}

- **ID**: 001-maintenance-core-module
- **Title**: Расчёт сроков и статусов в отдельном модуле maintenance-core
- **Context**: один расчёт нужен панели, плану и письмам; REQ-MAINT-001 и REQ-MAINT-002 требуют тестируемости и независимости от Spring и БД.
- **Options**: отдельный Maven-модуль; сервис Spring; функция PL/pgSQL.
- **Outcome**: выбранный вариант: «Отдельный Maven-модуль maintenance-core без Spring», потому что только он выполняет REQ-MAINT-001, REQ-MAINT-002 и раздел 3.5.5 SRS.
- **More Information**: [adr/0001-maintenance-core-module.md](../adr/0001-maintenance-core-module.md)

- **ID**: 002-service-record-single-transaction
- **Title**: Запись обслуживания, пробег и закрытие позиций в одной транзакции
- **Context**: частично сохранённое обслуживание искажает сроки; возможны параллельные изменения одного автомобиля.
- **Options**: одна транзакция с блокировкой строки; раздельное сохранение; оптимистическая блокировка.
- **Outcome**: выбранный вариант: «Одна транзакция PostgreSQL с блокировкой строки автомобиля», потому что он исключает частичное сохранение без повторного ввода.
- **More Information**: [adr/0002-service-record-single-transaction.md](../adr/0002-service-record-single-transaction.md)

- **ID**: 003-reminder-outbox-in-postgresql
- **Title**: События и задания на письма в PostgreSQL
- **Context**: REQ-REL-001 и REQ-REL-002 требуют идемпотентности и повторов, REQ-COST-001 – одного сервера.
- **Options**: outbox в PostgreSQL; отправка из проверки; брокер сообщений.
- **Outcome**: выбранный вариант: «Таблицы событий и заданий в PostgreSQL (outbox)», потому что он выполняет требования надёжности без дополнительного сервиса.
- **More Information**: [adr/0003-reminder-outbox-in-postgresql.md](../adr/0003-reminder-outbox-in-postgresql.md)
