# ADR-0002. Запись обслуживания, пробег и закрытие позиций плана в одной транзакции

## Контекст и постановка задачи

Сохранение записи журнала (REQ-FUNC-009) одновременно добавляет показание пробега и закрывает отмеченные позиции плана (REQ-FUNC-010): у них меняются дата и пробег последнего выполнения, а значит и следующий срок. Если запись сохранилась, а позиции нет, владелец увидит выполненную работу как просроченную. Как исключить частично сохранённое обслуживание и одновременное изменение одного автомобиля из двух вкладок?

## Драйверы решения

* Целостность журнала и плана (БЦ-2)
* REQ-SEC-003: каждая операция проверяет владельца автомобиля
* REQ-FUNC-004: новое показание не меньше предыдущего – проверка должна видеть актуальные данные
* Простота реализации одним разработчиком

## Рассмотренные варианты

* Одна транзакция PostgreSQL с блокировкой строки автомобиля
* Раздельное сохранение каждого объекта
* Оптимистическая блокировка по версии автомобиля

## Итог решения

Выбранный вариант: «Одна транзакция PostgreSQL с блокировкой строки автомобиля», потому что он единственный исключает частично сохранённое обслуживание без повторного ввода данных пользователем.

### Последствия

* Хорошо, потому что журнал, пробег и план всегда согласованы
* Хорошо, потому что проверка владельца и блокировка выполняются в одном месте
* Плохо, потому что длительные операции (загрузка вложений) нужно выносить за пределы транзакции

### Подтверждение

Интеграционный тест с Testcontainers: ошибка проверки пробега откатывает запись и закрытие позиций; два параллельных сохранения одного автомобиля дают корректную последовательность показаний; запрос к чужому автомобилю возвращает 404.

## Плюсы и минусы вариантов

### Одна транзакция PostgreSQL с блокировкой строки автомобиля

Сервис открывает транзакцию, проверяет владельца, блокирует строку `car` (`SELECT … FOR UPDATE`), сохраняет запись, расходники, показание и закрытие позиций.

* Хорошо, потому что ошибка любой проверки откатывает всю операцию
* Хорошо, потому что две вкладки одного владельца выполняются по очереди
* Плохо, потому что транзакция длиннее, чем при раздельном сохранении

### Раздельное сохранение каждого объекта

Запись, показание и позиции сохраняются отдельными вызовами.

* Хорошо, потому что каждый вызов проще
* Плохо, потому что сбой между вызовами оставляет частично закрытое обслуживание

### Оптимистическая блокировка по версии автомобиля

Поле `version` у автомобиля, конфликт – повтор операции пользователем.

* Хорошо, потому что нет ожидания блокировки
* Плохо, потому что пользователю приходится повторять ввод при конфликте

## Дополнительная информация

Вложения (REQ-FUNC-013) сохраняются в файловое хранилище до транзакции, а в транзакции записывается только ссылка; осиротевшие файлы удаляет ежедневная очистка. Связано с представлениями 006-interaction и 009-concurrency. Требования: REQ-FUNC-003, 004, 009, 010, REQ-SEC-003.
